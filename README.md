# Dream Almanac 365 · 梦历 365 · 本地相册的时间胶囊

> 把「删照片」重述成「寄存在梦里 365 天」。一年后，一封邮件把它还给你。

一个关于手机存储不足、相册取舍与断舍离的交互概念原型。\
**不是清理工具**：它不判断哪张该删，只让你亲手、慢一次地做决定。

---

## 它解决什么问题

手机提示「存储空间不足」时，系统按**文件大小**排序给你清理建议，却从不问哪张对你重要。\
而云盘往往还剩几百 GB——缺的不是空间，是一次决定。

梦历把删除操作改写成一次**寄存**：

| 常规清理 | 梦历 365 |
|---|---|
| 系统自动删 | 你亲手删 |
| 删完即消失 | 删后留空槽，标注可寄回日期 |
| 一次操作结束 | 365 天后一封邮件归还选择 |
| 强调「快」 | 强调「慢」 |

---

## 体验流程

1. **首屏**：本地 126.4 / 128 GB 已满，云端 412 GB / 2 TB 空着，相机无法拍摄。
2. **选择**：六组照片，每组标注大小与「上次打开」时间。系统不替用户选。
3. **确认**：全屏看最后一眼 → 手打组名才解锁删除（GitHub 删仓库式摩擦）。
4. **结果**：原图从本机移除，卡片变成虚线空槽，写「已从本机删除 · 2027.10.24 可申请寄回」。
5. **梦历页**：365 天进度条，寄存中的组数、云端占用、到期日；中途不提醒，直到第 358 天。
6. **邮件**：一年后寄回，只给三个数据（几组不在本机 / 一年打开几次 / 腾出的空间撑了几天）与三个动作（下载回本机 / 继续留云端 / 永久删除）。

另有一屏**代价演示**：两天后高铁进隧道，想给妈妈看毕业照——照片还在相册里，只是不在这台手机上。

## 设计主张

痛感不来自形容词，来自四个结构性条件：

1. **主动权在人**——必须你点、你看、你手打组名，系统不代劳。
2. **不可逆**——「本机删除」而非「移至别处」，不提供撤销。
3. **缺席可见**——删除后是空槽位，不是灰图；让缺失有形状。
4. **延迟兑现**——代价一年后才结算，且只陈述事实，不抒情。

**断 · 舍 · 离** 落在机制上：

- **断**：本地满了，必须先做决定，才能继续拍。
- **舍**：舍掉的是「随时能看」，不是云端那份。
- **离**：一年后知道它在哪儿，并愿意为它等 12 秒。

---

## 它的边界：什么条件下成立，什么条件下不成立

这是一个概念验证，不是商业产品。\
它验证的是一个假设：当删除不可逆、代价被延迟结算时，人会不会更认真地对待
"哪些照片值得留在本机"。

要变成产品，需要跨过四道门槛，目前四道都没过：

| 门槛 | 现状 |
|---|---|
| 需求方向 | 用户要"快、自动、别操心"，本产品要求"慢、手动、等一年" |
| 留存结构 | 一年只触达一次，月活趋近于零，订阅模型不成立 |
| 获客入口 | 系统存储弹窗归系统所有，第三方无法拦截 |
| 付费点 | 用户为"空间"付费，不为"仪式感"付费 |

它的价值不在商业闭环，而在产品思维样本：如何把一个默认
操作重新定义、如何用摩擦替代确认弹窗、如何把"删除"变成
可结算的承诺。

## 运行

单文件 HTML，无构建、无依赖、无后端：

```bash
# 方式一：直接打开（Chrome / Edge 可用）
open index.html

# 方式二：本地服务（推荐，避免部分浏览器的本地文件限制）
python3 -m http.server 8000
# 访问 http://localhost:8000
```
若 8000 被占用，换成`8080` 或`9000` 即可。\
删除记录保存在浏览器 `localStorage`（键名 `mengli365.v1`），刷新后空槽位与可用空间仍然保留。\
清空方式：浏览器开发者工具 → Application → Local Storage → 删除该键。
